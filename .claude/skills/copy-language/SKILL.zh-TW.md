# 文案語言（copy-language）

狀態：**草稿，2026-10-01**——主 session 根據網站現有文案和決策索引整理，使用者還沒審閱。

為什麼要有這份：文案過去都是一頁一頁各自決定，沒有共同依據，同樣的錯一再發生——`specs` 直接照設計稿上線成「寫到」（D-73）、「登記的關係」使用者看不懂只好改名（D-70）、網站名稱被問了兩次（D-32／D-65）、專案頁副標提案太白。每一件都是沒人寫下來的語氣或用詞問題。（`engineering-principles.md` 2026-10-01 補充：訪客看得到的文案不算「局部細節」。）

## 跟其他工具的分工

| 工具 | 負責 |
|---|---|
| 這份 skill | 字該怎麼寫：語氣、已定案用詞、格式 |
| `visual-design-language` | 字長什麼樣：字級、字重、顏色（含 D-68 的最小字級） |
| `mockup-fidelity:ux-review` | 讀者到底看不看得懂——每次改訪客文案都要跑（D-69） |
| Anthropic `design:ux-copy`（[原始碼](https://github.com/anthropics/knowledge-work-plugins/blob/main/design/skills/ux-copy/SKILL.md)） | 通用的介面句型（按鈕、錯誤、空狀態），下面有借用；它明確要求外部提供語氣和用詞——這份檔案就是那個外部來源 |

## 語氣

依據網站已經在用的文案（About、首頁），不是另外發明的：

- **第一人稱、白話。** About：「只收我自己寫過的文章、用過的技術、做過的專案。」用作者自己的口吻說有什麼。不用行銷腔（打造、賦能、一站式、探索…的旅程）。
- **用目錄的詞彙，因為網站本身就是一份目錄。** 目錄、編、類別、關係，是在字面上描述網站怎麼運作——About：「這套分類和雙向關係，來自我的圖書資訊學背景」——不是裝飾。首頁：「私人藏書，公開目錄」、「文章、技術與專案，編成可以查詢的目錄」。字面上成立的地方才用，不要硬套到它描述不了的東西上。
- **具體勝過泛泛。** 放在誰的網站都成立的句子（「做過的專案與技術」），就算沒錯也太白。優先寫只有這個網站才有的細節。
- **短。** 用最少的字保住意思（ux-copy 原則 2）。
- **依讀者背景選字**（使用者 2026-10-01）。訪客就是 `mockup-fidelity:ux-review` 已經在模擬的四種讀者：不懂技術的一般訪客、找證據的工程師／招募者、初階開發者、圖書資訊背景的讀者。選四種人都不用解釋就看得懂的字。後端用語和圖書館學術語（著錄、登記）都不用，除非句子本身有解釋。使用者對「登記」的判斷：放在一個後端工程師的網站上太文謅謅（「以一個後端而言是不是有點過於文謅謅」）。

## 已定案用詞——選字前先查這裡

| 用 | 不用 | 出處 |
|---|---|---|
| `IN / ARCHIVE`（站名、分頁標題、字標） | `jerrylib`、`Jerry in Archive`、`My Dev Grid` | D-32、D-60、D-65 |
| 直接關係（記在目錄裡的，實線）／間接關聯（推算出來的，虛線，只在首頁） | 登記的關係、推導關聯 | D-70 |
| 類別、三大類 | 型別 | D-68 |
| 關係動詞由兩端的類別決定：文件**說明**技術、文件**記錄**實作、技術**用在**實作 | 逐一翻譯每個述詞；`specs` 翻成「寫到」 | D-73（完整對照表仍未定） |
| 頁面標題維持原樣，英文也保留（`My Articles`、`Production Artifacts`） | 把標題翻成中文 | D-76 |
| 收在目錄裡、一筆一筆記下來（表達「記錄在目錄裡」） | 訪客頁用「登記」 | 使用者 2026-10-01（D-82） |
| 關聯對象（`/graph` 詳情卡表格裡「關係連到的東西」那一欄）；這兩個（間接關聯兩端的那一對） | 節點、連到的節點（圖論術語）；兩端（跟「兩邊都連到」並排容易混淆） | 使用者 2026-10-03（D-88） |
| `/graph` 詳情卡用簡短標示、不用句子：節點卡上下堆疊（標籤在上、名稱用頓號接），標籤為「版本／技術／實作／文件」；連線卡一行「a 類別　動詞 →　b 類別」，動詞為使用（實作→技術）、說明、記錄、需要、版本，其餘為「相關」，主詞在前 | 詳情卡裡的「用到它的實作」「說明它的文件」「相關的技術」「「Vue」用在「…」」（使用者：「經過圖形化的東西不該這麼口語」）；「起點／終點」列（跟「節點」同屬圖論用語）。經 ux-review 後從畫稿 C＋E2′ 選定。2026-10-04 起首頁的連線彈窗、滑過提示也用同一種一行寫法（畫稿 H；滑過提示是純文字「a（類別） 動詞 → b（類別）」），`relationPhrase` 的句子已拿掉 | 使用者 2026-10-03（D-88）；2026-10-04 延伸到首頁 |

跟使用者定下新用詞時，在這裡加一列，**同時**在決策索引加一列。

## 格式

**頁面副標**（頁面標題下面那一行）
- **只放在內容本身看不出用途的頁面**（使用者 2026-10-01，D-83）。內容一看就知道是什麼的清單頁——`/articles`、`/projects`——不放副標；首頁和 `/graph` 保留。沒有副標的頁面，第一屏仍要有一句中文（筆數、空狀態）。
- 描述這頁有什麼。**不寫操作說明**——控制元件畫面上本來就看得到（使用者 2026-10-01 否決了「…，可以用技術篩選」）。
- 資訊量大的字放前面：「讀者只看到前兩個字，也該抓到大意」（[NN/g](https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content/)）。
- 句尾不加「。」（D-68）。
- 跟同層頁面對齊：`My Articles` → 「開發筆記與技術文章」。

**段落說明**（段落標題下的一兩句）
- 完整句子，句尾加「。」（D-68）。說明讀者正在看什麼、怎麼讀（顏色、大小、線條），不講它是怎麼做出來的（D-76）。

**後台頁面**（文章管理／編輯、本體論編輯頁——要登入才看得到）
- **功能性的寫法就可以，上面的語氣規則不適用。** 目前只有作者自己用。使用者 2026-10-01：「後台文案可以隨意或功能性一點 反正現在只有自己用」（D-81）。後台專用的文案不用跑 ux-review（D-69 管的是訪客文案）。
- 已定案用詞（上面那張表）仍然適用，避免同一個東西有兩種叫法。
- 有其他人拿到帳號時再重新檢視。

**訪客頁的互動元件微文案**（句型借自 `design:ux-copy`）
- 錯誤訊息：發生什麼＋為什麼＋怎麼辦（「文章清單載入失敗，重新整理再試一次。」已經符合）。
  - **例外：載入失敗提示（`LoadFailedNotice`）是給站長看的，不是給訪客**（2026-10-02，使用者：「開發用語不需要吧 這我自己看的錯誤訊息而已」）。直接用開發用語寫出哪支請求、什麼狀態碼失敗，例如「資料載入失敗：GET /graph 回傳 HTTP 500，下面先放示範資料。」不要改寫成訪客用語，也不用跑模擬讀者審查。
- 空狀態：這是什麼＋為什麼是空的＋怎麼開始（有辦法開始的話）。

## 文案主張要對得上資料

文案裡每個具體的例子、數字、專案名稱、關係，都必須在實際資料裡找得到（API、seeder、同步進來的 GitHub 專案）。提案前就查，不要等讀者抓到。實例：About 的範例「這篇文章說明 Vue 3」，資料裡找不到對應的文章（2026-10-01 模擬讀者審查）。（概念借自 Copywriting Editor Kit plugin 的「主張對證據」檢查；plugin 本身沒有安裝。）

## 不要

- 訪客文案裡出現開發者用語：hover、邊、型別、已實現、套件名稱、程式識別名稱（D-68）。
- 叫觸控裝置的使用者「滑到」某處。
- 副標裡寫操作說明（見上）。
- 在 D-73 允許範圍以外的訪客頁面顯示英文述詞名稱。
- **比喻：適合就可以用，但不能拿來代替專案的事實**（使用者 2026-10-01，D-82）。適合讀者和頁面的比喻可以用（目錄的意象成立，是因為網站本來就是一份目錄）。只要是關於專案的內容——做了什麼、用了什麼、擔任什麼角色、有什麼成果——都必須照實寫：不用比喻代替事實，不編造例子（見「文案主張要對得上資料」）。實例（2026-10-01）：審查建議 About 寫成「我一筆一筆記下來」，但後端的 GitHub 同步會自動建立技術—專案（`uses`）和 `specs` 關係，寫「我親手記」不實。

## 流程

1. 先查這份檔案和決策索引裡已定案的用詞。
2. 出 2～3 個候選，每個附一句理由，對應上面某條規則；文案裡的主張要先對過資料。
3. 對實際畫面或設計稿跑 `mockup-fidelity:ux-review`（D-69）。
4. 使用者挑選；新定案的用詞或規則寫回這份檔案和決策索引。
