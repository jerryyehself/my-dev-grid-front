# 已知限制

這份清單記錄「我們知道、而且暫時選擇不處理」的限制，讓讀程式碼的人不用猜那段怪怪的寫法是不是疏忽。

- 每一條都要有**淘汰條件**：什麼情況發生後這條可以刪掉。沒有淘汰條件的限制不收，要嘛當 bug 修，要嘛不記。
- 每週上線（`develop` 合併進 `main`）時檢查一次：重新評估條件成立了沒、淘汰條件滿足了沒，滿足就修掉並刪除該條。
- 只寫技術事實：限制是什麼、影響多大。不寫怎麼觸發，也不寫還沒修好的安全問題（那類走私下回報）。
- 對應的程式碼旁邊有一行指向這裡的註解，標題要跟著對上。
- 行號是寫這份文件時的位置，程式碼動過就更新；找不到時以檔名與函式名為準。

## 舊的 PROJ 編號連結退回選最新專案

- **問題**：站點上線前流傳的 `?project=PROJ-YYYY-NN` 連結，現在對不到任何專案，專案頁會退回選清單第一筆（清單依建立時間由新到舊，所以是最新的專案）。舊的 PROJ 編號是前端依年份順序算出來的，新增專案就會位移，從來沒有穩定過。
- **影響**：點到舊連結的人看到的是最新專案，不是當初連結想指的那一個。站內連結已改用後端 id，不受影響。
- **為什麼現在不修**：舊編號不穩定，本來就無法對回正確的專案，沒有可以還原的資訊；做一個「找不到」的提示頁只會多一條維護路徑。
- **重新評估的條件**：不會重新評估，這是刻意的行為。
- **淘汰條件**：舊連結不再有人使用後，移除這個退回行為（找不到 id 時改成忽略參數或顯示找不到）。預計 2027-03 淘汰。
- **程式位置**：`src/features/projects/ProjectsView.vue:35-42`（讀取 `project`／`implementation` 參數與說明）、`src/features/projects/ProjectsView.vue:64-74`（選中的 id 不在清單時改選第一筆；篩選把選中的專案擠出清單時也走這段，淘汰時只處理「網址參數對不到」的情況，不要動篩選的行為）。

## 插入腳註不檢查游標是否在程式碼區塊內

- **問題**：編輯頁的「插入腳註」把 `[^N]` 直接插在游標處，不會判斷游標是不是在 fenced code block 或行內程式碼裡面。編號的計算有略過程式碼區塊，但插入位置沒有。
- **影響**：插在程式碼裡的 `[^N]` 會被當成程式碼文字顯示，不會變成腳註，而文末仍會補上對應的空定義。作者在輸入框與預覽都看得到，可以自己刪掉；不會遺失資料。
- **為什麼現在不修**：目前編輯器只有站主一個人在用，影響只是多按一次刪除；要判斷游標落在哪種程式碼語法裡，得重做一套跟渲染端一致的解析，成本高於這個問題。
- **重新評估的條件**：編輯器的使用者超過站主一人，或腳註插入改成自動執行（不再由作者手動按）。
- **淘汰條件**：編輯器或腳註功能被取代時一併移除。
- **程式位置**：`src/features/articles/insertFootnote.ts:88-107`（`insertFootnote()`，插入位置 `at` 在第 90 行算出）；呼叫端 `src/features/articles/ArticleEditorView.vue:252`。

## Technique／Implementation 沒有手動編輯介面

- **問題**：`Technique`、`Implementation` 這兩種實體只由後端的 GitHub 同步建立，前端沒有任何介面能手動新增或修改。`Documentation`（文章）已經可以在文章編輯頁新增與編輯，分類與述詞的定義（`Scope`、`Relation`）也有管理頁，都不在此限。
- **影響**：這兩種實體的內容只能靠同步更新，同步沒帶進來的欄位無法手動補或修正，前端只能不顯示。
- **為什麼現在不修**：資料來源以 GitHub 為準，手動編輯會和下一次同步互相覆蓋，需要先決定衝突時誰優先，這是後端與前端要一起設計的功能。
- **重新評估的條件**：同步無法涵蓋的資料欄位變多，或需要手動修正同步結果的情況反覆出現。
- **淘汰條件**：前端有這兩種實體的編輯介面，或同步機制被取代。
- **程式位置**：前端目前只有讀取端，`src/api/projects.ts:119`（`fetchProjects()`）；管理頁的清單見 `README.md`「管理頁面」一節。
