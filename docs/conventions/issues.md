# 開 issue

寫給開 issue 的人。Codex 照 `AGENTS.md` 一輪挑一張 `codex` issue、開一張 PR，所以**一張 issue 就是一張 PR 的範圍**。

## 段落

每張 `codex` issue 都用這四段，標題文字照抄：

```
## 背景
## 要做的事
## 驗收條件
## 範圍外
```

- **背景**：現況和為什麼要改。指向 repo 裡的檔案或規則（例如 `docs/conventions/testing.md`），不寫只有維護者知道的脈絡。
- **要做的事**：逐點列。要改的檔案寫完整路徑，包含清單類檔案（例如 `eslint.config.ts` 的例外清單）。
- **驗收條件**：寫成能用指令判斷過或不過的條件。行為改動寫具體的輸入和預期輸出（例如 `# A`、`# A-2`、`# A` → `a`、`a-2`、`a-3`）。最後一條固定寫「`AGENTS.md` 列的檢查指令全部通過」。
- **範圍外**：不能碰的檔案、不能改的函式名稱或行為。至少寫「上面沒列的檔案」。

## 大小

- 大小看**改動種類**，不看檔案數。一張 issue 只放一種可以單獨審、單獨合併的改動。
- **同一種機械式改動開一張**，不管有幾個檔案：把同一條規則套到很多檔案、改名、改 import 路徑都算。前提是驗收能靠 lint 或測試自動判斷，而且 diff 每處的改法都一樣。
- 一張 PR 太大、一輪做不完時（大約超過 50 個檔案或 1000 行），可以分批，但**一次只開一張**，前一張合併後再開下一張。
- 不同種類的改動分開，例如修 bug 和改測試標題分成兩張。
- 不夾帶「順便」的事。想到的另外開，或寫進範圍外。

## 合併還是拆開

| 情況                                           | 做法                                       |
| ---------------------------------------------- | ------------------------------------------ |
| 同一種改法套到多個檔案                         | 一張                                       |
| 兩件事會改到同一個檔案                         | 一張；要分就依序開，前一張合併後才開下一張 |
| 兩件事不共用檔案，各自審、各自合併都不會壞東西 | 分開                                       |
| B 要等 A 做完才能做                            | 分開，A 合併後才開 B                       |

- **不要同時開著兩張會改到同一個檔案的 `codex` issue。** 清單類檔案（`eslint.config.ts`、`package.json`、`src/router/`）最容易撞到。開新 issue 前，先看開著的 `codex` issue 和 `codex/` PR 有沒有列到相同的檔案。
- 例：把 33 個測試檔的標題改成「它應該…」，並把它們移出 `eslint.config.ts` 的例外清單 → 開一張。拆成五張的話，五張都要改例外清單、彼此衝突，CI 和審查也要做五次。

## 前後順序

- Codex 從編號最小的開始挑，不看「blocked by」。有前後依賴的，後面那張等前一張合併後再開，不要先開好排隊。
- 引用其他 issue 一律寫編號（`#162`），不寫「前一張 src/api 那張」。

## 標籤

- `codex` 加上**恰好一個** `area:` 標籤（`test`、`deps`、`markdown`、`graph`、`components`、`auth`…，需要時新增）。
- 修 bug 加 `bug`，新功能加 `enhancement`。
- 還在討論、還不能動手的 issue 不要標 `codex`，Codex 一看到就會開工。

## 標題

- 寫要達成的結果：`標題錨點：原標題自帶流水號時不應產生重複的 slug`。
- 用繁體中文。檔名、函式名維持原文。

## 不能寫

這是公開 repo。issue 內文、標題、留言都不寫：

- 私有文件裡的決策或待辦編號
- 維護者的原話、對話內容
- 私有 repo 的路徑、沙箱的本機路徑
- 密鑰、正式環境資料、個人資料
- 還沒修好的漏洞細節。這類問題不開 issue。

## 不交給 Codex 的事

要判斷好不好看、好不好讀的事（設計、文案、視覺、動態），以及登入授權、部署設定、CI、資料庫結構，都不開 `codex` issue。
